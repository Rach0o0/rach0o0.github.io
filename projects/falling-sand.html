Case study 06 · GPU / Godot

A falling-sand simulator, running on the GPU

A cellular-automaton sand simulation built in Godot 4, with the actual physics running as a GLSL compute shader: 65,536 grid cells updated in parallel, every frame.

EngineGodot 4 (GDExtension, C++)
ShaderGLSL compute
TeamAyoub Agouzoul & me
Why GPU

65,536 cells, each an independent tiny problem

A falling-sand automaton is embarrassingly parallel: whether a cell becomes sand or empty next frame depends only on itself and its immediate neighbors. On a 256×256 grid, that's 65,536 independent little decisions every step, exactly the kind of workload a GPU is built for, and a natural excuse to go past the CPU and write an actual compute shader.

Architecture

Double-buffered textures, ping-ponged every frame

The grid lives as two GPU textures. Each frame, the compute shader reads the current one and writes the next state into the other (never both at once), which sidesteps the classic parallel-write race condition of updating a grid in place while other threads are still reading it. Once the shader finishes, the two textures swap roles for the next frame.

if (current == EMPTY && above_cell == SAND) {
  next = SAND;
} else if (current == SAND && below_cell == EMPTY) {
  next = EMPTY;
}
set_cell(coord, next); // written to the OTHER texture
Engineering details

Built to degrade gracefully

01

C++ GDExtension bridge

A native C++ SandGrid class (extending Godot's Sprite2D) owns both the CPU cell array and the GPU RenderingDevice pipeline, exposing simulation controls to the Godot editor and GDScript.

02

Automatic CPU fallback

If GPU compute setup fails on a given machine, the extension falls back to an equivalent single-threaded CPU simulation automatically: same rule, same visuals, just slower.

03

Built-in benchmarking

A timing mode measures wall-clock time and step count until the grid reaches a stable state, printed directly from the engine, and used to compare the CPU and GPU code paths against each other.
