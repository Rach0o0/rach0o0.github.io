A chess engine, from minimax to bitboards

A four-person C++ project building a chess engine from the ground up: legal move generation, search, evaluation, and an opening book, pushed from a naive prototype to a genuinely fast bitboard engine.

Evolution

From a random-move bot to a real engine

The engine wasn't built in one shot. It went through clear stages, each one driven by a concrete bottleneck the team hit.

01

Legal moves & a random-move bot

Starting from a king-only board, the team built out piece logic, castling, en passant, and promotion, then had the engine play legal random moves as a first milestone.

02

Minimax → alpha-beta pruning

A first minimax search worked but was slow. Switching to alpha-beta pruning cut the search tree dramatically without changing the result: the same best move, reached much faster.

03

Migrating to bitboards

Profiling showed the array-based board representation was the bottleneck. Rewriting piece storage and move generation around 64-bit bitboards sped up move generation by roughly 5–10×.

04

Zobrist hashing & move ordering

A compile-time-generated Zobrist hash table (built from an LFSR at compile time) gives every position a near-unique 64-bit key. Combined with MVV-LVA capture ordering, killer moves, and principal-variation-first ordering, the search explores far fewer bad branches before finding good moves.

05

Opening book

My part: translating an external openings database into a lookup table mapping board positions to strong opening moves, via a Python preprocessing script, so the engine doesn't have to search the most well-known openings from scratch.

Under the hood

A few implementation details

Negamax with quiescence search

Search is a negamax variant with alpha-beta pruning, extended with quiescence search at leaf nodes to avoid misjudging positions mid-capture-sequence. A time-limited search mode uses setjmp/longjmp to cleanly abort deep searches once the time budget runs out, always returning the best move found so far.

namespace Search {
  int Quiesce(Board &board, int alpha, int beta, PV &pv);
  int Negamax(Board &board, int alpha, int beta, int depth,
           int searchDepth, PV &pv, SearchLimit *limit);
  BitMove BestMoveTime(Board &board, int time_limit);
}

Tapered evaluation

The evaluation function doesn't use fixed piece-square tables. Instead, it computes a game phase from remaining material, then blends middlegame and endgame piece-square values accordingly. A king that's well-protected in the middlegame should push toward the center in the endgame, and the tapered evaluation captures that transition smoothly instead of switching abruptly.

Move ordering: MVV-LVA

Alpha-beta pruning is only as good as the order moves are searched in. I implemented MVV-LVA (Most Valuable Victim – Least Valuable Attacker) capture ordering, trying "queen takes pawn" before "pawn takes queen", on top of killer-move and principal-variation-first ordering, so the search finds strong moves earlier and prunes more of the tree.
