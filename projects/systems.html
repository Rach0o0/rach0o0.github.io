Case study 05 · Systems / C

A concurrent server that races against SHA-256

An Operating Systems course challenge: build a multithreaded server that finds SHA-256 preimages inside a given range, as fast as possible, under real concurrent load, and prove which scheduling strategy handles that load best.

LanguageC, pthreads
CourseOperating Systems, DTU
My focusPriority scheduling experiment
The challenge

Reverse a hash, fast, under pressure

Clients send a SHA-256 hash, a numeric search range [start, end), and a priority byte. The server has to brute-force which number in that range hashes to the given value, and answer as quickly as possible, while many clients hit it at once, each with different priorities, difficulties, and patience. The interesting part isn't the brute force itself; it's how the server stays fast and fair when it can't serve every request instantly.

Architecture

One accept loop, a shared priority queue, a pool of workers

Each worker pulls the highest-scoring request, checks a custom hash cache first, and only falls back to brute force if it's a miss. Cache buckets are aligned to 64 bytes to sit cleanly on a cache line, and results are shared across all workers behind a mutex, so once one client's hash has been cracked, every future identical request is instant.

found = cache_get(&cache, hash64, req->hash, &found_answer);
if (!found) {
  found_answer = find_answer(req->hash, req->start, req->end, &found);
  if (found) cache_put(&cache, hash64, req->hash, found_answer);
}
My contribution

Designing and testing the priority scheduler

A plain FIFO queue ignores priority entirely, and a naive "always serve the highest priority" queue starves low-priority clients under load. I designed and benchmarked five scheduling strategies, then built a hybrid scorer that balances all three signals at once:

score(r) = α · priority_norm(r) − β · difficulty_norm(r) + γ · age_norm(r)

α isn't fixed: it scales up as the queue gets longer, so priority matters more precisely when the server is under real pressure. The age_norm term guarantees that no request waits forever, no matter how low its priority: the longer it sits in the queue, the more its score climbs.

StrategyBehaviour
FIFO (baseline)Ignores priority entirely, pure arrival order.
Strict priorityHighest priority always served first, fast, but risks starving low-priority clients.
Weighted round robinPriority sets service frequency, balanced and fair.
AgingPriority rises with wait time, no starvation, even under heavy load.
Hybrid (mine)Combines priority, difficulty, and age into one adaptive score, most responsive under stress.

Each strategy was benchmarked across four priority distributions (from "no priority" to "strong priority"), plus dedicated difficulty, repetition, and load-stress tests, 10 runs each. The result was consistent: FIFO leaves performance on the table by ignoring priority, strict priority wins on latency but isn't fair, and the hybrid scheduler gave the best overall balance, especially once the server was under real stress.
